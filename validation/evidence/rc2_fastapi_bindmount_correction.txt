=== diep-fastapi bind-mount correction (2026-06-26) ===

ROOT CAUSE: the live diep-fastapi container had been brought up via
`docker compose` invoked from the main checkout directory
(/home/emmanoff_lab/projects/diep-lab, branch feature/adms-topology-import)
at some point before this qualification engagement began. docker-compose.yml's
fastapi service uses a relative bind mount (`./fastapi:/app`), which resolves
against whatever directory `docker compose` was run from -- not against
whichever git worktree/branch is "intended." Confirmed via
`docker inspect diep-fastapi --format '{{range .Mounts}}...'`:
  BEFORE: /home/emmanoff_lab/projects/diep-lab/fastapi -> /app
This meant every restart of diep-fastapi (including the one performed
earlier this sprint to deploy the /telemetry/latest auth fix) re-read code
from the main checkout, not the RC worktree
(.claude/worktrees/dlms-driver-validation, branch release/v1.0-rc-qualification)
where all qualification and remediation work has actually happened. The
auth fix committed to fastapi/app.py was real and correct but was NOT live
until this correction -- confirmed by `docker exec diep-fastapi grep -n
"def latest_telemetry"` showing the old, pre-fix signature even after a
`docker compose restart fastapi`.

Same class of issue already documented for diep-ingestor (Post-SIT
stabilization sprint) and mosquitto/config/acl (this engagement's earlier
session) -- a recurring pattern: a standalone compose file or a relative
bind-mount path existing is not proof of what's actually live; verify per
service with `docker inspect <container> --format '{{json .Mounts}}'` and
the compose project labels, every time, don't generalize from one fix.

Scope check: `diff -rq` between the main checkout's fastapi/ and the
worktree's fastapi/ shows app.py, common.py, and 6 router files
(automation.py, controls.py, dms.py, oc_flisr.py, oms.py, topology.py)
differ -- confirmed via `git status --short fastapi/` in the main checkout
that these are committed branch divergence, not stray uncommitted edits.
The docker-compose.yml `fastapi:` service block itself is byte-identical in
both locations -- this was purely a "which directory was `docker compose`
run from" issue, not a config drift issue.

CORRECTION: recreated only the diep-fastapi container, same compose
project ("diep-lab"), same network/container name/ports/env, sourced from
the RC worktree:

  docker compose -p diep-lab --project-directory \
    /home/emmanoff_lab/projects/diep-lab/.claude/worktrees/dlms-driver-validation \
    -f docker-compose.yml up -d --no-deps --force-recreate fastapi
